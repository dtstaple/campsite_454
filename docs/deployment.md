# Deployment

How CampSite runs in production on [Render](https://render.com), and how to deploy, redeploy,
refresh the data and roll back.

**Status (2026-11-08).** The repo is deploy-ready (TM05-161): `render.yaml` defines all three
services, CI deploys after it passes on `main`, and the image, settings, data restore and smoke
test were checked locally against production settings ([What was tested](#what-was-tested)). The
production deployment itself, on paid plans from `dtstaple/campsite_454`, is not created yet;
that needs the Render account owner (the HUMAN steps in
`artifacts/run-report-2026-11-08-sprint9.md`).

The first deployment, TM05-113 (Oct 20, 2026), still runs on Render's free tier from Bleron
Balidemaj's fork, `BleronBalidem/campsite_454`: https://campsite-web-tt5e.onrender.com and
https://campsite-api-70v0.onrender.com. Its free database expires around Nov 19, 2026, has no

## Architecture

```
 browser ──HTTPS──▶ campsite-web   static site on Render's CDN: frontend/dist (React + MapLibre)
    │                              basemap tiles come straight from Stadia Maps
    └────HTTPS──▶ campsite-api    Docker web service: gunicorn + Django (backend/Dockerfile)
                        │          /api/... JSON and vector tiles, /admin, /static (whitenoise)
                        ▼
                  campsite-db     Render Postgres 16 + PostGIS, private network only
```

- The browser loads the frontend from `campsite-web`, then calls the API at
  `VITE_API_BASE_URL`. The two are different origins, so the API allows the frontend's origin
  through CORS.
- Only `campsite-api` talks to the database, over Render's private network (the internal
  connection string). The external URL is used only from a laptop, to restore data.
- TLS ends at Render's proxy. Django trusts `X-Forwarded-Proto` (`BEHIND_TLS_PROXY=True`),
  redirects HTTP to HTTPS, and marks cookies `Secure`.
- Location (the GPS dot, Follow me) needs HTTPS, which Render provides on both services.

## The services

Everything is in **`render.yaml`** (a Render Blueprint). No secret value is committed:
`SECRET_KEY` is generated by Render, `DATABASE_URL` is wired from the database, and the
`sync: false` variables are typed into the dashboard when the Blueprint is applied.
`tests/test_deploy_config.py` checks all of this.

### `campsite-db`: PostgreSQL 16 + PostGIS

- **Plan `basic-256mb`, 5 GB disk.** The snapshot restores to about 1.2 GB; the disk can grow
  later but never shrink. A paid plan does not expire (free ones do after 30 days) and has
  backups (below).
- **PostGIS** is enabled by `scripts/restore_production.sh` (`CREATE EXTENSION IF NOT EXISTS
  postgis`), so it is not a manual step.
- **Backups.** Paid Render databases have point-in-time recovery: **campsite-db → Recovery**
  restores the database to a moment in the recovery window into a new database. The length of
  the window depends on the workspace plan; check it on that page. Independently, everything
  but accounts and saved items can always be rebuilt from the snapshot release.

### `campsite-api`: the Django backend

- **Docker**, built from `backend/Dockerfile` on plan **`starter`** (512 MB, does not sleep).
  The image installs GDAL/GEOS from Debian, runs `collectstatic` at build time (whitenoise
  then serves the admin's files), runs as a non-root user, and starts gunicorn with
  `WEB_CONCURRENCY` workers (default 2) and a `GUNICORN_TIMEOUT` (default 180 s).
- **Migrations on deploy.** `preDeployCommand: python manage.py migrate --no-input` runs
  once per deploy, after the build and before the new version takes traffic. If it fails,
  the deploy stops and the previous version keeps serving. `MIGRATE_ON_START=False`, so the
  start command does not migrate again. (The image's default, `True`, is for hosts without a
  pre-deploy step, such as Render's free plan or `docker run`.)
- **Health check.** `healthCheckPath: /api/health/`. Render routes traffic to a new version
  only once this returns 200, and restarts an instance that stops answering. The path is
  exempt from the HTTPS redirect. The image also has a Docker `HEALTHCHECK` on the same path.
- **Memory.** Measured locally under a 512 MB limit with 2 workers, after both had loaded
  the routing graph: 367 MB.

### `campsite-web`: the static frontend

- **Static site** from `frontend/`: `npm ci && npm run build`, publishing `dist/`, on
  Render's global CDN with HTTPS.
- **SPA rewrite**: every path serves `index.html`, so `/discover` and the other client routes
  load directly.
- **Headers**: hashed `/assets/*` are cached for a year (`immutable`); `index.html` is
  `no-cache`, so a deploy shows at once; `nosniff` and a referrer policy on everything.
- `VITE_API_BASE_URL` and `VITE_MAP_STYLE_URL` are **baked in at build time** (see
  [The frontend](#the-frontend-a-static-build)), so changing either means rebuilding.

## Deploying

### The first deployment

The click-by-click list is the HUMAN checklist in `artifacts/run-report-2026-11-08-sprint9.md`.
In short:

1. In Render, **New → Blueprint**, connect `dtstaple/campsite_454`, branch `main`. Render
   reads `render.yaml` and asks for the four `sync: false` values. Enter placeholders for the
   two origins and two `VITE_*` values if the URLs are not known yet, and correct them after
   step 2.
2. Once the services exist, set `CORS_ALLOWED_ORIGINS`/`CSRF_TRUSTED_ORIGINS` on the API to the
   frontend's URL, and `VITE_API_BASE_URL` on the frontend to the API's URL, then redeploy
   both. Add the frontend's domain to the Stadia property.
3. Load the data: [Production data](#production-data).
4. Add the two deploy hooks as GitHub secrets.
5. Check it: [Checking a deploy](#checking-a-deploy), then a real iPhone.

### Every merge to `main`

1. The PR is merged; CI runs on `main` (`quality` and `frontend`).
2. Only if both pass, the `deploy` job calls the two deploy hooks. While the secrets are not
   set, the job prints that it skipped.
3. Render builds the API image, runs the pre-deploy migrations, starts the new version, waits
   for `/api/health/`, and then switches traffic (zero downtime). The frontend rebuilds and
   publishes.

Render's own auto-deploy is off (`autoDeployTrigger: "off"`), so a red CI run never deploys.

### Redeploying by hand

- **Same commit again:** the service → **Manual Deploy → Deploy latest commit**. For the
  frontend after changing a `VITE_*` value: **Clear build cache & deploy**.
- **An environment variable on the API:** Environment → edit → **Save, rebuild, and deploy**.
- **A new frontend or backend URL** means these four must agree:
  `CORS_ALLOWED_ORIGINS` and `CSRF_TRUSTED_ORIGINS` (API), `VITE_API_BASE_URL` (frontend, then
  rebuild), and the Stadia property's domain list.

## Production data

Production is filled from the team snapshot, the same file developers restore
([data-status.md](data-status.md)). From a laptop with `make setup` done:

```
scripts/restore_production.sh '<External Database URL>?sslmode=require' \
    https://github.com/dtstaple/campsite_454/releases/download/dev-data-2026-11-08/campsite-2026-11-08.dump
```

- The URL is **campsite-db → Connect → External Database URL**. Keep it in your shell only:
  never in chat, Jira, a commit or a file in the repo. Quote it.
- The script asks you to type the database's host name before it changes anything (`--yes`
  skips the question).
- It **refuses a database that already has data** unless `--force` is added, because a
  restore replaces every table, **production accounts and saved items included**.
- It creates PostGIS if missing, restores (skipping the entries a non-superuser may not
  create), runs the migrations, and prints row counts. It reuses `scripts/snapshot.py`, the
  code behind `make restore`, which was tested on a throwaway database over TLS.

### Refreshing production data

A new snapshot replaces everything, including users. Before running the restore with
`--force`:

1. Take a recovery point: note the time, so **Recovery** can return to it.
2. Tell the team that accounts made on the live site will be lost, or export them first:
   ```
   pg_dump '<External URL>' --data-only --format=custom \
       -t auth_user -t authtoken_token -t 'accounts_*' -t 'planning_*' -f people.dump
   ```
   Keep `people.dump` out of the repo. Restoring it afterwards only works if the campsite and
   trail IDs it refers to are unchanged in the new snapshot.
3. Run the restore with `--force`, then the smoke test.

## Rolling back

- **Code.** The service → **Events** → a previous successful deploy → **Rollback**. Render
  redeploys that build without rebuilding. Do it for the API and the frontend separately.
  Note: rollback turns that service's auto-deploy off; here it is already off, and the CI hook
  keeps working, so the next merge deploys normally.
- **A migration.** Rolling back code does not undo a migration. If the old code cannot run
  on the new schema, either fix forward, or reverse the migration first from a laptop
  (`DATABASE_URL='<External URL>' .venv/bin/python backend/manage.py migrate <app> <previous>`),
  then roll the code back.
- **Data.** **campsite-db → Recovery** restores to a point in time into a new database; then
  point `DATABASE_URL` at it. For geodata only, re-running the restore script from the
  snapshot is enough.

## Checking a deploy

```
scripts/smoke_test.sh https://<campsite-api URL> https://<campsite-web URL>
```

It checks health, that DEBUG is off, the frontend and a client route, CORS, map data, a
vector tile, a trail panel with its elevation profile, Find campsites on that trail, route
planning on the trail graph, register, sign in, save/list/unsave a campsite and sign out, and
then deletes its throwaway account. It exits non-zero on any failure. The first Find campsites
for a trail samples USGS 3DEP and can take a minute or two; run `make prewarm` against
production (`DATABASE_URL='<External URL>' make prewarm`) before a demo to cache the demo
trails.

Then, on a real iPhone over the live URL: the map and basemap with its attribution, Location
(the GPS dot), Follow me, a trail panel, Find campsites, planning a route, and Add to Home
Screen.

## Background

The sections below explain the choices behind the setup.

### The database: PostGIS, not just Postgres

The app requires the **PostGIS extension**, so a plain PostgreSQL database is not enough.
Every geometry column, spatial index, and bounding-box query in `/backend/api` depends on
PostGIS types and functions. GeoDjango's first `migrate` runs
`CREATE EXTENSION IF NOT EXISTS postgis`, and against a server without PostGIS installed
that fails before any table is created. PostGIS is a server-side extension that has to be
installed on the database host. Nothing in our code can install it, so a hosting provider
is only usable if it offers PostGIS.

When choosing a managed Postgres, check three things in its current documentation:

- **PostGIS is on the provider's list of supported extensions.** Most large managed
  services offer it, but some free tiers don't.
- **Who is allowed to run `CREATE EXTENSION postgis`.** PostGIS is not a "trusted"
  extension, so on many providers only an admin role can enable it. The simplest pattern
  is to enable it once as the admin (`CREATE EXTENSION postgis;`) and let the app's role
  do everything else. After that, migrate's `IF NOT EXISTS` is a no-op. `reset_db` never
  drops or recreates the extension, so it keeps working under a non-admin role.
- **Versions.** Development and CI use PostgreSQL 16 with PostGIS 3.4
  (`postgis/postgis:16-3.4`). A hosted database should match the Postgres major version,
  especially if data is ever moved across with `pg_dump`.

Providers give out connection strings like `postgres://user:pass@host:port/db?sslmode=require`.
That string is the whole of the configuration: `settings.py` always forces the PostGIS
engine regardless of the URL scheme, and query parameters such as `sslmode=require` are
passed through to the driver. Characters like `@` or `/` in a password must be
percent-encoded (`@` becomes `%40`). The settings keep connections open for 10 minutes
(`conn_max_age=600`), so a small plan's connection limit needs to cover roughly one
connection per web-server worker.

**Getting data into a hosted database.** A fresh database is empty, and there are three
ways to fill it:

- **The team snapshot**, the normal way: `scripts/restore_production.sh` for production
  ([Production data](#production-data)), or `make restore` for a dev database
  (docs/setup.md, path C). Both create PostGIS if it is missing, restore, and migrate.
- `python manage.py seed` loads the committed sample (the Essex Chain Lakes: one 7 × 7 km
  patch). This is enough to show the app working.
- `python manage.py ingest <source> <region>` runs the real pipeline straight into the
  hosted database from any machine with network access, then `build_route_profiles`,
  `enrich_campsites`, `build_trail_graph` and `make terrain`. It is reproducible but takes
  hours.

### The backend: getting GDAL and GEOS

This is the least obvious part of deploying a GeoDjango app. `django.contrib.gis` loads
the **GDAL** and **GEOS** C libraries when Django starts, and it refuses to start if it
can't find them. They are operating-system libraries, not Python packages, so
`pip install -r requirements.txt` does not provide them.

On a Mac, developers install them with Homebrew and point Django at them in `.env`:

```
GDAL_LIBRARY_PATH=/opt/homebrew/opt/gdal/lib/libgdal.dylib
GEOS_LIBRARY_PATH=/opt/homebrew/opt/geos/lib/libgeos_c.dylib
```

Those are Apple Silicon Homebrew paths. They don't exist on Windows, Linux, Intel Macs, or
any hosting platform, so **these two variables are development-only and must not be set in
production.** They are needed on macOS only because Django 5.1 looks for GDAL by versioned
file name, only for versions 3.0 through 3.8, and Homebrew currently ships a newer GDAL.
When the variables are unset, Django searches the system's default library paths. That
works wherever a supported GDAL version is installed the normal way.

The dependable way to provide the libraries in a deployed environment is a **Docker image
that installs them from the Linux distribution's package manager**. Debian bookworm ships
GDAL 3.6 and GEOS 3.11, which Django finds automatically. This image was built and used to
run the whole app for this story (migrations, seeding, the API server, and the full test
suite):

```dockerfile
FROM python:3.12-slim-bookworm
RUN apt-get update \
 && apt-get install -y --no-install-recommends libgdal32 libgeos-c1v5 libproj25 \
 && rm -rf /var/lib/apt/lists/*
COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt
WORKDIR /app
```

It installs only the runtime libraries (about 590 MB uncompressed), not the `-dev`
headers, because nothing in `requirements.txt` compiles against GDAL. It is a starting
point, not a production image. It still needs the application code copied in, a
production web server (see below), a non-root user, and a start command. CI
(`.github/workflows/ci.yml`) takes the same approach on an Ubuntu runner with `apt-get`.

The alternative is a platform that provides GDAL itself, such as a buildpack or a
platform-specific package list. That can work, but the platform has to give Django a GDAL
version it recognises (3.0–3.8 as of Django 5.1). If it ships something newer,
`GDAL_LIBRARY_PATH` has to be set to that platform's own path. A Docker image avoids that
guesswork.

The same image is also a way for **Windows developers** to avoid installing GDAL natively,
which is notoriously awkward on Windows (typically OSGeo4W or conda). Nobody on the team
has tested that path on Windows yet.


### The frontend: a static build

`npm run build` (run in `/frontend`) type-checks the app and writes `index.html` plus
hashed JS and CSS bundles to `frontend/dist/`. Those files are the whole frontend. Any
static host can serve them: a CDN or static-site service, an object-storage bucket with a
website endpoint, or the same nginx that fronts the backend. No Node.js server runs in
production.

**`VITE_API_BASE_URL` is baked in at build time, not read at runtime.** Vite replaces
`import.meta.env.VITE_API_BASE_URL` with the literal string while building, so the value
in effect when `npm run build` runs is hard-coded into the JavaScript bundle. Two things
follow from that:

- Pointing the frontend at a different backend means **rebuilding it**. Changing an
  environment variable on the static host does nothing. Set the value in
  `frontend/.env.production` (gitignored) or in the build environment before building.
- The value is **public**. Anyone can read it in the bundle, so no `VITE_*` variable may
  ever hold a secret.

The build warns that the JS bundle is about 1.5 MB (427 KB gzipped), almost all of it
MapLibre. That is acceptable for now, but it could be split later.


## Moving between databases (dev tooling)

Three management commands in `backend/devdata` make any database usable in one step.
They are plain Python, so they run identically on macOS, Windows, and Linux, with no
shell scripts, Makefiles, or Postgres client tools. Run them from `/backend` with
`DATABASE_URL` pointing at the target:

- `python manage.py seed` loads the committed sample fixture
  (`backend/devdata/fixtures/sample.json`, ~490 KB) into an empty, migrated database. It
  refuses if the database already has features, because fixture rows have fixed primary
  keys and would overwrite real rows.
- `python manage.py reset_db` drops every app table, re-runs migrations, and seeds. It
  asks for confirmation; `--noinput` skips the prompt. It never drops the schema or the
  PostGIS extension.
- `python manage.py build_sample` regenerates the fixture from the live sources for the
  sample area. It needs network access and an **empty scratch database**, and is only
  needed when the models or adapters change. No API key is needed: campsites come from
  OpenStreetMap. It fails, and leaves the committed fixture unchanged, if any layer comes
  back empty or the file would exceed 1 MB.

The sample is a small bounding box around the Essex Chain Lakes, in the Adirondacks, with
geometries clipped to the box. It sits inside the map's opening view, so a freshly
seeded app shows data without panning. It used to be Crawford Notch, NH, because
campsites then came only from RIDB, which needs a key, and because an earlier Adirondack
box found only an invalid Forest Preserve polygon in PAD-US. Neither holds now: OSM
campsites are keyless, and PAD-US returns individual Forest Preserve units there. The
large White Mountain National Forest parcel is still skipped as invalid, so the largest
public-land units may be missing from the full database.

  parses to the PostGIS engine with `sslmode` passed through.
- `ruff check`, `ruff format`, and the full pytest suite pass. The suite includes tests
  for the seed, reset, and sample tooling.
- `npm install` and `npm run build` succeed.
- `manage.py check --deploy` and `collectstatic` were run to find the gaps listed above.

Not tested:

- **A real hosting provider.** The second database was a local container. A managed
  service adds TLS, network allow-lists, connection limits, and extension permissions,
  none of which were exercised.
- **Windows.** The commands contain nothing OS-specific, and the fixture is UTF-8 with
  `\n` line endings, but nobody has run them on Windows. A Windows teammate should run
  `migrate`, `seed`, and `reset_db` once.
- **A production web server, HTTPS, or a static host** serving `frontend/dist`.
- **The built frontend talking to a deployed backend.** The frontend doesn't call the API
  yet.

## Local development gotchas found along the way

- **Another Postgres on port 5432.** If a native PostgreSQL (e.g. from Homebrew) is
  running, it can take `localhost:5432` ahead of Docker, so Django reaches the wrong
  server and fails with `role "campsite" does not exist`. Set `POSTGRES_PORT=5434` (or any
  free port) in `.env`, use the same port in `DATABASE_URL`, and run
  `docker compose up -d` again.
- **The PostGIS image is x86-only.** `postgis/postgis:16-3.4` has no ARM build, so on
  Apple Silicon Docker runs it under emulation. It works, just more slowly.
